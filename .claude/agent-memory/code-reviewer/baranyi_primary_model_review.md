## Context
`predictive/primary/baranyi.py` (+ `predictive/primary/__init__.py`, `tests/unit/test_baranyi.py`) is a new, additive, unwired module: Baranyi-Roberts primary growth model ported from a validated frontend TS implementation, plus a new closed-form inverse `time_to_target()` with no frontend equivalent. Confirmed clean of `app.*` imports; `predictive/engines/combase/` untouched by the diff. See `specs/lessons.md`'s "2026-08-22 — Baranyi primary growth model" entry (long, several sub-sections) and `specs/specifications.md` §5.6 for the full history — both are unusually thorough and, as far as I could independently verify, honest (they explicitly flag a reviewer claim — a "15-37 h0 imprecision band" — that did NOT survive the implementer's own independent check, and document why).

Prior rounds (not reviewed by me directly, reconstructed from lessons.md/code comments) found and fixed, in order:
1. Direction bug in ALREADY_MET (sign vs. direction confusion for declining/inactivation scenarios) — caught by the round-trip test itself.
2. Two independently-rounded near-singularity checks (a reachability guard and the `z`-formula's `denom`) disagreeing in sign at the boundary — fixed by deriving both from one shared `denom`.
3. `h0>0` time-inversion computing `exp(h0)*(exp(mu_abs*a_star)-1)+1` directly — silent `inf`/crash for realistic 12-30h growth/inactivation durations. Fixed with a log-sum-exp (`expm1`/`log1p`) reformulation.
4. `h0 >= ~37.5` making `expm1(-h0)` underflow to exactly `-1.0`, driving `log1p()`'s argument to/past its domain floor. Fixed with `if term_diff <= -1.0: return UNREACHABLE`.
5. `math.exp((target_y_ln-y0_ln)/cm)` overflowing directly in the growth branch (independent of h0) when `cm` is small (y_max close to y0) and the target is far beyond reach. Fixed by computing `shifted = exponent - m_curv` via plain arithmetic and short-circuiting on `shifted >= 0` before ever exponentiating.

## What I independently verified (third pass)
- All 74 existing tests pass (`pytest tests/unit/test_baranyi.py`).
- `mypy predictive/primary/`, `black --check`, `ruff check` all pass clean.
- No `app.*` imports anywhere under `predictive/`; `predictive/engines/combase/{engine,calculator,models}.py` untouched by `git diff`/`git status`.
- The `term_diff <= -1.0` guard is exactly correct and sufficient: `term_diff = exp(-mu_abs*a_star) * expm1(-h0)` is algebraically confined to `[-1, 0]` by construction (first factor in `(0,1]` since `a_star>=0` is enforced upstream; second factor in `[-1,0]` since `h0>=0` is enforced by `BaranyiParams.__post_init__`) — so `-1.0` is the *only* boundary value that can occur, `math.log1p(-1.0)` itself raises `ValueError` (confirmed directly), and values merely close to `-1.0` (e.g. `-0.9999999999999998`) return large-but-finite `log1p` results, not crashes — matching the documented "15-37 band is imprecise, not broken" characterization.
- The `shifted >= 0` guard is sound: `exponent = target_ln/cm` is provably `>= 0` given the upstream guards (target_ln and cm always share sign), so `shifted` can be `+inf` (if `cm` underflows toward 0 while staying nonzero) but never negative-when-it-shouldn't-be; `shifted >= 0` correctly catches both the ordinary "past asymptote" case and the `+inf` case without ever calling `math.exp()` on the dangerous argument.
- Independent bisection-oracle cross-check (2000 random cases, h0 up to 30, |mu| up to 5, targets ±30, `population_at`-only — never calls `time_to_target`'s own algebra) found **zero classification mismatches and zero time-value mismatches (>1% rel. err)** against `time_to_target`'s REACHED/UNREACHABLE/ALREADY_MET output. This is a stronger check than crash-freedom fuzzing — it validates *correctness*, not just *doesn't-throw*.
- My own 50,000-iteration fuzz sweep (wider than the module's own 5,000-iteration `TestLargeH0CrashGuard` sweep: h0 up to 400, |mu| up to 1000, targets up to ±1e10, asymptote gaps spanning 1e-15 to 1e-300) found **zero crashes** — the existing fixes are robust across a very wide realistic-to-extreme envelope.

## NEW finding: a genuine 5th crash, ZeroDivisionError via subnormal-float underflow of `cm`
Reproducible directly (not via a probabilistic fuzz hit — required deliberate construction, see below):
```python
params = BaranyiParams(initial_log_cfu=0.0, y_max_ln=1e-323, mu_max_ln=1.0, is_growth=True, h0=0.0)
time_to_target(params, target_log_increase=0.001)  # -> ZeroDivisionError: float division by zero
```
Mechanism: in the `is_growth=True` branch, `cm = (y_max_ln - y0_ln) / m_curv` (line ~295) is computed *before* the `shifted >= 0` guard (line ~311) that was specifically added (fix #5 above) to prevent overflow in this exact region of the function. When `y_max_ln - y0_ln` is a positive float small enough that dividing by `m_curv=10.0` underflows to exactly `0.0` (true once the raw difference is `<= ~1e-323`, i.e. within a couple of ULPs of the smallest subnormal double `~4.94e-324`), `cm == 0.0` exactly. The very next line, `exponent = (target_y_ln - y0_ln) / cm`, then divides by that exact zero and raises `ZeroDivisionError` — a crash the existing `shifted >= 0` guard never gets a chance to prevent, because computing `exponent` (which requires dividing by `cm`) happens *before* `shifted` can even be computed.

This is structurally the *same class* of bug as fix #2 above (a degenerate/near-singular case slipping past the guard meant to catch it) — the top-of-function degenerate guard `(y_max_ln - y0_ln) * mu_ln <= 0` checks the *sign* of the product, which is satisfied (product is a tiny positive nonzero float, not exactly zero) even when the difference itself is about to underflow to zero on division. It is one level "upstream" of every fix applied so far.

**Realistic reachability, calibrated honestly:** confirmed via `math.nextafter` that this requires `y0_ln` to be *exactly* `0.0` (i.e. `initial_log_cfu == 0.0` exactly — plausible, e.g. a single-CFU/g starting inoculum) **and** `y_max_ln` to be a literal subnormal-magnitude float (~1e-323, i.e. differing from `0.0` by roughly the smallest representable positive double) — not merely "close to zero" in any normal sense. My 50,000-iteration wide fuzz sweep, and the module's own 5,000-iteration sweep, both used gap magnitudes with a `uniform(0.001, ...)` or similar floor and never got remotely close to this; when I deliberately widened my own fuzzer's gap range down to `1e-15`-`1e-300` added onto a *nonzero-magnitude* `y0_ln` (e.g. `y0=3.0`), the addition rounds the tiny gap away entirely before the subtraction ever sees it, so the bug did not reproduce there either — it is specific to `y0_ln` landing on `0.0` (or, by the same mechanism, any exact float) with `y_max_ln` placed within about 1 ULP of the smallest subnormal of that value. No realistic ComBase-CSV-derived or RAG-derived value would ever be constructed this way. Severity: **MEDIUM** — a genuine, reproducible crash for a "non-degenerate per the guard's own test" input, but reachable only via adversarial float placement several hundred orders of magnitude below any physically meaningful precision, in contrast to the four prior fixes which all fired at moderate/realistic parameter magnitudes (h0 in the tens-to-hundreds, cm around 0.1-1, targets in the tens).

**Suggested fix** (not applied — review-only): guard `cm` for exact/near-zero before dividing by it, mirroring the existing `denom <= _NEAR_ASYMPTOTE_EPS` pattern already used a few lines later in the same branch, e.g. `if cm == 0.0: return BaranyiInverseResult(UNREACHABLE, None)` immediately after computing `cm`, or reorder to check `abs(y_max_ln - y0_ln) <= <epsilon>` before dividing by `m_curv` at all.

## Process note for future rounds
The pattern across all 3 review rounds on this file: each fix's own reasoning implicitly narrowed what the *next* fuzz pass happened to probe (explicitly named in lessons.md as a lesson already). My contribution extends it one more step: even a structural "every math.exp() call is bounded" argument (which the implementer explicitly made and which holds) can leave a *different* operation — a plain division by a derived, cancellation-prone denominator — unguarded. When auditing a near-singularity fix, check every arithmetic operation between the raw subtraction and the "designed" guard, not just the exponentiations the guard was written to protect.
