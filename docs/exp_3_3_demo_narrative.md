# PTM Model Selection — Demo Narrative (Exp 3.3)

For the advisory board. ~5-minute walkthrough. Tells the story of the model-comparison experiment, the production recommendation, and what we learned about local-model alternatives.

---

## The question

When a user types a food-safety scenario into PTM, the system uses a large language model to read it and extract the structured information underneath — what food, what pathogen, what temperature, what duration, and what kind of model the system should run (will the food grow bacteria, or will it kill them?).

That last classification — **growth vs thermal inactivation** — is the most safety-critical step in the pipeline. If the system mistakes a cooking scenario for a storage scenario, it picks the wrong conservative bound and the safety verdict flips. Get this wrong, and a "this food is unsafe" call becomes a "this food is safe" call, or vice versa.

So we needed to answer two questions:

1. **Which model should run in production?**
2. **If budget constraints make frontier models infeasible, which local model is the next-best option — and what would it take to make it actually viable?**

---

## What we tested

We tested seven models against a benchmark of 20 expert-annotated queries. The queries span easy cases (everything is specified explicitly) through to hard adversarial cases drawn from real PTM failure history — including the "chicken nuggets bug" (a cooking scenario that earlier versions of the system mistakenly classified as growth) and the turkey-temperature-range case (where the user gives a range like 10–15°C and the system must preserve the range, not collapse it to a midpoint).

Each query was run 20 times per model — both to measure accuracy and to check how consistent each model is on identical inputs.

The seven models split into two classes:

- **Frontier models** — accessed via OpenAI's API. GPT-4o (current production) and GPT-5.5.
- **Local models** — run on our own hardware via Ollama. Qwen 3 8B, Phi-4 14B, Llama 3.1 8B, Gemma4 (a smaller Google model), and GLM-4.7 Flash.

GLM-4.7 had an API key configuration issue and is excluded from this run — re-running it is on the to-do list but doesn't change the conclusions.

---

## What we found

### The headline: GPT-4o stays in production

| Model | Overall accuracy | Model_type accuracy | Cost per call |
|---|---|---|---|
| **GPT-4o** | **96.0%** | **90.0%** | **$0.014** |
| GPT-5.5 | 95.5% | 90.0% | $0.026 |
| Qwen 3 8B (best local) | 79.8% | 75.0% | $0.000 |
| Phi-4 14B | 78.6% | 45.0% | $0.000 |
| Llama 3.1 8B | 69.7% | 25.0% | $0.000 |
| Gemma4 | 51.8% | 5.0% | $0.000 |

GPT-4o has the highest overall accuracy, the highest accuracy on medium-difficulty queries, and the lowest cost per call. It correctly handles the chicken-nuggets case. It meets every production criterion. **No reason to switch.**

GPT-5.5 is essentially tied on accuracy but costs nearly twice as much per call — the small accuracy difference doesn't justify the cost difference.

### The harder finding: no local model is currently good enough

For PTM, the safety-critical floor we set is **95% accuracy on the model_type classification** — no more than 1 misclassification in 20. None of the local models clears it.

- Qwen 3 8B: 75% — the best of the local models, but 20 percentage points below the floor
- Phi-4 14B: 45% — fails on the chicken-nuggets case
- Llama 3.1 8B: 25% — fails on most queries
- Gemma4: 5% — gets only 1 of 20 right

What's striking is that **the largest local model we tested (Phi-4 at 14B parameters) does worse than the smaller Qwen at 8B**. This is consistent with what we found in the embedder experiment: for PTM-specific reasoning, parameter count is not the bottleneck. Scaling up to bigger off-the-shelf models is not the answer.

### A real example of why this matters

The chicken-nuggets case (H1): "Chicken nuggets reached about 68°C instead of 74°C, held for roughly 8 minutes. Are they safe?"

This is a cooking scenario — the user is asking about an inadequate cook step. The right classification is **thermal_inactivation**. If the system instead classifies it as **growth**, it picks the wrong worst-case bound, and the safety verdict reverses.

| Model | Got it right? |
|---|---|
| GPT-4o | ✓ |
| GPT-5.5 | ✓ |
| Qwen 3 8B | ✓ |
| Phi-4 14B | ✗ |
| Llama 3.1 8B | ✗ |
| Gemma4 | ✗ |

Three of the four local models fail the most important single test in the benchmark.

## So what's the path forward for local models?

We identified three things that need to improve before any local model is production-viable:

1. **Model_type accuracy must reach 95%.** Qwen is at 75%, so the gap is 20 points. The most promising route to closing this gap is **domain fine-tuning** — training Qwen on PTM-style queries with the correct extractions, generated by GPT-4o. Roughly 1–2 weeks of work for a first iteration.

2. **Schema compliance must reach 100%.** Qwen produces malformed output on roughly 1 in 8 calls. Fixable with stricter prompting and an application-level retry layer.

3. **Latency tail must drop below 30 seconds.** Qwen's P95 latency is currently 60 seconds, but most of that is hardware contention on the dev workstation. Production deployment on dedicated hardware would likely halve it.

There's also a pragmatic intermediate option: a **hybrid architecture**. The local model handles most queries; when it produces an ambiguous or low-confidence answer, the system escalates to GPT-4o. Best of both worlds — local-by-default for cost, frontier-on-demand for safety. Worth prototyping as the next experiment.

---

## What this experiment taught us beyond the model choice

Three things worth keeping:

1. **Field-level scoring with a safety-critical distinction matters.** If we only looked at overall accuracy, GPT-4o (96%) and Phi-4 (78.6%) would look like a 17-point gap. Looking at model_type accuracy specifically, the gap is 45 points (90% vs 45%). The right metric for the production decision is the safety-critical one — not the average.

2. **Consistency was high across all models.** Even Gemma4 — which gets the model_type wrong 19 times out of 20 — gets it wrong the same way every time. This matters for fine-tuning: the local models' failures are *systematic*, which means they're learnable. A model that randomly fluctuates is much harder to improve.

3. **Parameter count is a weaker signal than training quality.** The 14B Phi-4 lost to the 8B Qwen by 30 percentage points on model_type. Whatever Qwen's training process was, it produced a model that handles classification reasoning better than a model 75% larger. Encouraging for the local-improvement path: we don't need bigger, we need better-trained.

---

## The recommendation, in one line

**Keep GPT-4o in production. The best path to local viability is fine-tuning Qwen 3 8B on PTM-specific data — not scaling up to a bigger off-the-shelf model.**

---

## What we have now that we didn't before

Two artefacts that outlive this experiment:

- A **20-query benchmark with expert ground truth** that we can re-run against any future model change — a new prompt, a new model, a fine-tuned variant.
- A **clear safety-critical floor** (95% on model_type accuracy) that gives future model decisions an objective gate, not a judgement call.

Both will be reused for the next round of model experiments — including the fine-tuning work that this experiment makes the case for.
